# Building & Composing Containers

## Writing a good Dockerfile

```dockerfile
FROM node:20-slim
WORKDIR /app
COPY package*.json ./        # copy manifests first...
RUN npm ci                   # ...so this layer caches when only code changes
COPY . .
EXPOSE 3000
CMD ["node", "server.js"]
```

- **Layer caching:** order instructions least- to most-frequently-changing. Copying
  `package.json` before the source means dependency installs are cached across code edits.
- **`.dockerignore`** keeps `node_modules`, `.git`, and secrets out of the image.
- **`CMD` vs `ENTRYPOINT`:** `ENTRYPOINT` sets the fixed executable; `CMD` provides default args.

## Multi-stage builds (smaller images)

```dockerfile
FROM node:20 AS build
WORKDIR /app
COPY . . && RUN npm ci && npm run build

FROM nginx:alpine                       # tiny runtime image
COPY --from=build /app/dist /usr/share/nginx/html
```
Build tooling stays in the first stage; only the artifact ships.

## Volumes — persistent data

Containers are ephemeral; volumes outlive them.
```bash
docker run -v pgdata:/var/lib/postgresql/data postgres:16
```
Named volumes (managed by Docker) for databases; bind mounts (`./src:/app/src`) for live-reload in
dev.

## Networks — service-to-service

Containers on the same user-defined network reach each other **by service name**.
```bash
docker network create appnet
# then `web` can call `http://api:4000` and `postgres:5432`
```

## docker-compose — the whole stack

```yaml
services:
  web:   { build: ., ports: ["3000:3000"], depends_on: [db] }
  db:    { image: postgres:16, volumes: ["pgdata:/var/lib/postgresql/data"] }
volumes: { pgdata: {} }
```
`docker compose up -d` starts everything on a shared network — exactly how this platform runs
Postgres + API + web.
