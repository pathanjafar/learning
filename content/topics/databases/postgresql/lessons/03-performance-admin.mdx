# Postgres Performance & Administration

## Indexing strategy

```sql
CREATE INDEX idx_email ON users (email);                  -- B-tree (default)
CREATE INDEX idx_data ON docs USING GIN (data);            -- JSONB / arrays / full-text
CREATE INDEX idx_geo ON places USING GIST (location);      -- geometric / range
CREATE INDEX idx_active ON users (email) WHERE active;     -- partial index
```

- **B-tree** — equality & ranges (the default).
- **GIN** — many-valued columns (JSONB, arrays, full-text).
- **GiST** — geometric, range, nearest-neighbor.
- **Partial / expression** indexes target specific rows or computed values.

## Analyzing queries

```sql
EXPLAIN ANALYZE SELECT * FROM orders WHERE user_id = 42;
```
Spot sequential scans on large tables, bad estimates (run `ANALYZE` to refresh statistics), and
expensive joins. `REINDEX` rebuilds bloated indexes.

## Full-text search

```sql
SELECT * FROM articles
WHERE to_tsvector('english', body) @@ to_tsquery('postgres & index');
```

## Partitioning

Split a huge table into chunks (by range/list/hash) so queries scan only relevant partitions —
essential for time-series and very large tables.

## VACUUM & maintenance

Postgres uses **MVCC**, leaving dead row versions behind. **`VACUUM`** reclaims them; **autovacuum**
runs automatically — tune it for write-heavy tables to avoid bloat.

## Backup & recovery

- **`pg_dump`/`pg_restore`** for logical backups.
- **PITR** (point-in-time recovery) via WAL archiving.
- **Streaming replication** for high availability and read replicas.

## Security & connections

- **Roles** with `GRANT`/`REVOKE`; **Row-Level Security (RLS)** restricts rows per user.
- Require **SSL** connections.
- Use a pooler like **PgBouncer** — Postgres connections are heavyweight, and apps (via ORMs like
  Prisma/SQLAlchemy) should pool rather than open one per request.
